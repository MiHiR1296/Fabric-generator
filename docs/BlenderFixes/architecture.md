# Parametric Weave knotty — architecture

> **Read this if** you're about to touch a socket, an internal link, or any of the per-material switch chains in the .blend, OR you need to know how `bandMeta.blender.*` data flows from the producer through the node group to the rendered pixels.

## Object / modifier stack

```
ParametricWeave (mesh, 0 verts of its own — geometry is generated by modifiers)
├── Weave            (Nodes modifier → Parametric Weave knotty)        ← what this doc is about
└── Fit To Space     (Nodes modifier → Fit Geometry To Space Plane)    ← scales output to fit Space plane
```

`WebDraft_Live` is a separate hidden mesh object (one face per drawdown cell, with `cell_code` / `warp_material_id` / `weft_material_id` face attributes). Built by [backend/app/blender_sync.py:build_blender_sync_code](../../backend/app/blender_sync.py) before each render. The Weave modifier reads it via the `Draft Object` socket.

## Where bandMeta lands

For each ready yarn asset, the backend calls `build_material_asset_entry(asset)` ([backend/app/blender_live.py](../../backend/app/blender_live.py)) which flattens `asset.bandMeta.blender.*` into the 9-field dict the live-push and headless paths both consume. The 1-based Material N index maps to the socket family:

| Producer key (`bandMeta.blender.*`) | Lands on socket | Drives |
|---|---|---|
| `image_width_px` | `Material N Image Width Px` | U-axis world-width per repeat |
| `texture_scale_u * material_texture_scale_u` | `Material N Texture Scale U` | Per-yarn U multiplier after Image Width Px. Phase 4i puts the fit/divide-by-10 correction here. |
| `core_v_min` | `Material N Arc 1 V Min` | Raw core lower V edge from metadata. Phase 4c padding happens inside the .blend after material selection. |
| `core_v_max` | `Material N Arc 1 V Max` | Raw core upper V edge from metadata. Phase 4c padding happens inside the .blend after material selection. |
| `fiber_bot_v_min` | `Material N Arc 2 V Min` | Strand silhouette's bottommost V |
| `fiber_top_v_max` | `Material N Arc 2 V Max` | Strand silhouette's topmost V |
| `scanner_pixels_per_bu` | (global) `Scanner Pixels Per BU` | Pushed from first asset only — DPI calibration |

The legacy inner-edge keys `fiber_top_v_min` and `fiber_bot_v_max` are still emitted into the entry dict (mirror of `core_v_max` and `core_v_min` by construction) for diagnostics, but no socket reads them after Phase 3e.

> **For the full mapping** (every metadata field, including render settings, pinned footgun defaults, draft-driven inputs, plus a worked example with thread001 values) see [../putting-it-together/data_contract.md → Complete mapping reference](../putting-it-together/data_contract.md#complete-mapping-reference--metadatajson--blender-modifier-sockets). This page focuses on the .blend-side mechanics; the data-contract doc owns the full producer↔consumer table.

## The switch chain — how Material N gets selected per face

The 96 V-band sockets are NOT read directly by the Map Range nodes. Each per-material socket flows through a 16-deep chain of `Switch` nodes that picks the correct value per face based on the `material_id` attribute (which `PW Warp Material Id` / `PW Weft Material Id` write upstream).

Concretely for V Min:

```
Material 1 Arc 1 V Min ──┐
Material 2 Arc 1 V Min ──┤
   …                     ├─→ PW Material Core V Min Select 2..16  (cascading switches)
Material 16 Arc 1 V Min ─┘
                          └─→ output: "active material's Arc 1 V Min for this face"
                                       │
                                       └─→ feeds into PW Band - Arc1 Map.To Min  (and Arc2 Core.To Max / Arc2 Bot.To Min)
```

The switch node names still say "Core V Min" (internal naming — wasn't renamed in Phase 3d because the rename was on the interface only). What they output is whatever Material N Arc 1 V Min is set to on the modifier for the currently-rendered face's material.

## The Arc 1 / Arc 2 system

The graph already labelled its internal nodes Arc 1 / Arc 2, but the interface sockets used the older Core / Fiber vocabulary until Phase 3d brought them in sync.

### Arc 1 — single-section mapping (used when sub-strand is OFF)

`PW Band - Arc1 Map` is one Map Range:

```
From [0, 1]  →  To [Arc 1 V Min, Arc 1 V Max]
```

Phase 4c exposes `Arc 1 V Padding` on the modifier and inserts it after the material switch chain. Phase 4h sets its default to `0.012` and lets the Web UI push the same socket:

```text
Padded Arc 1 V Min = max(Material Arc 1 V Min - Arc 1 V Padding, Material Arc 2 V Min)
Padded Arc 1 V Max = min(Material Arc 1 V Max + Arc 1 V Padding, Material Arc 2 V Max)
```

`PW Band - Arc1 Map` and Arc 2's inner core boundaries read the padded values. Backend metadata stays raw; the modifier panel owns this tuning value.

Maps the whole strand cross-section to the padded core V range. Result: the strand surface samples only the dense core texture, no halo. This is the **fallback path** when there's no sub-strand geometry.

### Arc 2 — three-section mapping (used when sub-strand IS ON)

Three Map Range nodes partition the cross-section coordinate (`v_around`) at `Split Minus` and `Split Plus`:

```
v_around                    Map Range            Texture-V range
─────────                   ─────────            ───────────────
[0, Split Minus]    →   PW Band - Arc2 Top  →  [Arc 2 V Max, Arc 1 V Max]   (outer top → core top)
[Split Minus, Split Plus] → PW Band - Arc2 Core → [Arc 1 V Max, Arc 1 V Min] (core top → core bottom)
[Split Plus, 1]     →   PW Band - Arc2 Bot  →  [Arc 1 V Min, Arc 2 V Min]   (core bottom → outer bottom)
```

The three outputs go through "Weighted" nodes and `PW Band - Arc2 Sum A` + `PW Band - Arc2 V` (both ADD nodes) to combine into one piecewise V value per face.

**The Phase 3e rewire moved 4 links** so the Top/Bot sections pull from the correct switch chains (`Core V Max Select` and `Fiber Top V Min Select` for Top; `Fiber Bot V Max Select` and `Core V Min Select` for Bot). Before the rewire, Arc 2 Top and Bot both mapped into the core's V range, making the halo invisible.

**The Phase 3k direction fix swapped the To Min / To Max links** on all three Arc 2 Map Range nodes. `v_around=0` is the top outer edge and `v_around=1` is the bottom outer edge, so Arc 2 must run from outer top → core top → core bottom → outer bottom. Without this flip, the halo was present but inverted within each end band.

### How Arc 1 and Arc 2 combine — `PW Band - Band V`

`PW Band - Band V` is a MULTIPLY_ADD node:

```
Band V = is_sub_strand × (Arc2 V − Arc1 Map) + Arc1 Map
```

- `is_sub_strand` = 0 on main strand geometry  →  Band V = Arc1 Map  →  core only, no halo
- `is_sub_strand` = 1 on sub-strand geometry  →  Band V = Arc2 V    →  halo + core + halo

The `is_sub_strand` attribute is set during sub-strand geometry generation, which only happens when **`Sub Strand Enable = True`**.

That's why `Sub Strand Enable` is pinned True in the producer's `PINNED_FOOTGUN_SOCKETS` ([blender_live.py](../../backend/app/blender_live.py)) — without it the rendered yarn has no halo, regardless of how good the Arc 2 V values are.

### Split Minus / Plus — centered Arc 1 inside Arc 2

```
core_frac = (Arc 1 V Max - Arc 1 V Min) / max(Arc 2 V Max - Arc 2 V Min, 0.0001)
Split Minus = 0.5 - core_frac / 2
Split Plus  = 0.5 + core_frac / 2
```

Phase 3m keeps Arc 1 geometry fixed and centers Arc 1's texture span inside Arc 2's wider silhouette. The extra Arc 2 area on either side maps the fuzzy/fiber halo. This replaces Phase 3h's measured top/bottom halo split for the active experiment.

For the current `black_white_thread` yarn:

| Value | Fraction |
|---|---|
| `core_frac` | 12.264% |
| `Split Minus` | 43.868% |
| `Split Plus` | 56.132% |

The old top/bot halo fraction nodes and the dead `r` nodes may still exist in the graph as visual leftovers, but they no longer feed `PW Band - Split Minus` / `PW Band - Split Plus`.

## Texture U mapping

The U direction maps generated strand length → texture U. The active graph already compensates generated curve length before the final texture scale:

```
Warp/Weft U Compensated = Spline Parameter Factor × (Spline Length / Straight Length)
Final U scale           = Straight Length / texture_world_width × root Texture Scale U × Material N Texture Scale U
```

Those two pieces collapse to actual generated spline length:

```
Factor × (Spline Length / Straight Length) × Straight Length = Factor × Spline Length
```

The texture-width part is built around three values:

```
texture_world_width_m = image_width_px / scanner_pixels_per_bu

(scanner_pixels_per_bu = dpi × 39.3701, so for 1600 dpi it's 62992.16)
```

A strand of generated length L wraps the texture L / texture_world_width_m times before scale multipliers. For thread001 (45058 px @ 1600 dpi -> 0.715 m per repeat), a 1 m strand shows 1.4 repeats.

The graph computes the raw strand length before the `Fit To Space` modifier:

```
source_strand_length_BU / (image_width_px / scanner_pixels_per_bu)
  * root_texture_scale_u
  * Material N Texture Scale U
```

For scan-driven yarns after Phase 4i, [blender_sync.py](../../backend/app/blender_sync.py) keeps root `Texture Scale U` neutral and computes a per-material multiplier:

```
texture_u_calibration = 0.1  # override via renderSettings.textureUCalibration or FABRIC_TEXTURE_U_CALIBRATION
root_texture_scale_u = 1.0
material_texture_scale_u = (max(Space X/Y) * Fill Ratio) / (Warp Threads * Spacing) * texture_u_calibration
Material N Texture Scale U = bandMeta.texture_scale_u * material_texture_scale_u
```

The producer pre-computes the measured width and pushes the raw `image_width_px` to `Material N Image Width Px`; the graph divides by `Scanner Pixels Per BU` internally to get world width. `bandMeta.texture_scale_u` remains the per-yarn/artistic override, defaulting to `1.0`, and the render/setup script multiplies it by `material_texture_scale_u` before pushing the socket. Phase 4d canonicalizes the user-tested divide-by-10 behavior as a calibration default, not as a unit conversion.

## Materials — the routing chain

```
Object material slots          Geometry node "Set Material" nodes
─────────────────────          ─────────────────────────────────
Slot 0  ←  WebYarn_<id>  ←──── Material 1 (NodeSocketMaterial input socket)
                                │  modifier socket Socket_61
                                │  LINKED to 'Set Material'.Material  (Group Input)
                                ↓
                          PW Set Material 2..16 inputs
                                ↓  modifier sockets Socket_62..Socket_204
                                ↓  LINKED (via PW Input - Material Slots Group Input)
                                ↓  to PW Set Material 2..16.Material
                                ↓  Selection = (PW Material Is N) gates by material_id
```

The "live" rendered material per face = whatever sits on the modifier's **Material N** input for the material id that face was tagged with. Slot 0 of the object is a fallback only; the real driver is the modifier's Material N socket.

This was the source of the "looks like wrong material" symptom in mid-Phase-3f / 3h — setting `Set Material.inputs[Material].default_value` does nothing because the input is link-driven from the Group Input. You have to set `mod["Socket_61"] = <Material>` instead.

As of Phase 3h, the Render Preview script creates one generated material per yarn asset (`FabricStudioMaterial_XX_<asset>`), appends those materials to the object slots, then sets `Material 1`, `Material 2`, etc. on the modifier. The old atlas material path remains as fallback when direct material entries are unavailable.

## Backend ↔ Blender wire formats

Two paths exist:

1. **Headless render** — backend writes a per-job Python script under `runtime/render_jobs/<id>/render_job.py`, spawns `blender -b <blend> --python <script>`. The script:
   - Builds WebDraft_Live mesh (via `build_blender_sync_code`)
   - Sets every modifier input that has data behind it (with `maybe_set_modifier_input` to silently skip sockets that don't exist on the current graph revision)
   - Creates direct per-yarn preview materials for <=16 assets, using full-resolution UDIM tiles when a scan exceeds the Cycles single-texture cap, otherwise Cycles-safe diffuse + alpha textures, all with `Linear` interpolation
   - Appends those materials to object slots and sets modifier `Material N` sockets
   - Inlines `APPLY_METADATA_PY` and calls `_pw_apply_modifier_material_metadata` to push per-Material V-bands and pinned defaults
   - Pushes Warp/Weft material cycle inputs so draft color bindings select the right `Material N`
   - Configures atlas material only as fallback when direct material entries are missing
   - Renders with `bpy.ops.render.render(write_still=True)` to `runtime/render_jobs/<id>/preview.png`
   - Phase 4f pins preview quality at `3200 × 3200`, Cycles, `96` samples, with denoising on. Override with `WEAVE_PREVIEW_RENDER_RESOLUTION` / `WEAVE_PREVIEW_RENDER_SAMPLES` for debugging or server runs.

2. **Live MCP render** (Phase 3g dev mode) — backend sends the same script body via `send_blender_command("execute_code", {"code": ...})` to the BlenderMCPAddon socket on port 9876. The open Blender session executes against the user's current scene and writes to the same `preview.png` path. Toggled by `BLENDER_LIVE_RENDER=1` env var. See [phase_log.md](phase_log.md) Phase 3g.

3. **Setup-only live push** (Phase 3i Pattern Builder mode) — `/api/blender/push-project-bandmeta` sends the same setup body with `render_still=False`. This updates `WebDraft_Live`, object material slots, modifier `Material N` sockets, Warp/Weft material cycles, and V-band metadata, then skips `bpy.ops.render.render(...)`. Important edge case: when the same yarn asset is assigned to warp and weft, only `Material 1` is populated and `Material 2..16` are cleared.

Both use the same script generation (`build_headless_render_script` in [render_jobs.py](../../backend/app/render_jobs.py)). Only the executor differs.

## Pinned defaults — Rule 3

These six sockets must stay at their pinned values for scan-driven yarns. The five V-related sockets are **additive deltas**, not absolute overrides, so leaving them at zero/one keeps the main-strand and sub-strand V mappings aligned:

```
Sub Strand Enable      True      # gates Arc 2 — see is_sub_strand chain above
Texture Scale V        1.0       # multiplier on V (1 = no scale)
Texture Offset V       0.0       # constant V shift (0 = no offset)
Texture Side Flatten   0.0       # cylindrical projection weight (0 = flat ribbon mapping)
Sub Texture Scale V    0.0       # additive delta on V for sub-strand (0 = aligned with main)
Sub Texture Offset V   0.0       # additive offset for sub-strand
```

Producer pushes these every time via `PINNED_FOOTGUN_SOCKETS` in [blender_live.py](../../backend/app/blender_live.py). Don't change them without reading lessons.md Rule 3.
